## 1. תקציר מנהלים

### 1.1 מה זה Cleana+

מערכת SaaS מבוססת ענן לניהול תורים עצמאי. במקום שבעל המקצוע יתאם תורים טלפונית או בהתכתבות, הוא פותח במערכת "חלונות טיפול" (ימים ושעות פנויים), מקבל קישור אישי, ושולח אותו ללקוחותיו. הלקוחות משבצים את עצמם לזמן שנוח להם, והמערכת מנהלת את הלוח באופן אוטומטי.

### 1.2 מה שונה מהמצב הקיים

| היום | עם Cleana+ |
|---|---|
| התכתבות ווטסאפ מתישה לתיאום כל תור | קישור אחד, הלקוח בוחר בעצמו |
| "מתי אתה פנוי?" × 30 לקוחות | חלון זמן אחד שכולם רואים |
| תורים כפולים / טעויות ביומן | המערכת חוסמת אוטומטית |
| תזכורות ידניות | תזכורות אוטומטיות |
| אין תמונה של מה קורה השבוע | דשבורד עם כל התורים |

### 1.3 המודל העסקי בשורה אחת

**Subscription טהור.** בעל המקצוע נרשם, בוחר מסלול, ומשלם דמי מנוי חודשיים קבועים. הקשר העסקי הוא **אך ורק** מול בעל המקצוע — המערכת אינה נוגעת בכסף שעובר בין המטפל ללקוח, אינה גובה עמלה על טיפולים, ואינה מחזיקה מידע רפואי.

### 1.4 החלטות מפתח שהתקבלו

| החלטה | נימוק |
|---|---|
| ✅ Web SaaS (לא Desktop App) | גישה מכל מקום, עדכון מרכזי אחד, ללא תחזוקת גרסאות OS |
| ✅ Subscription בלבד, ללא עמלות | מוריד מורכבות רגולטורית ופיננסית דרמטית |
| ✅ ללא סיכומי מפגש / מידע רפואי | מוריד חשיפה משפטית, מקצר time-to-market |
| ✅ קהל יעד מורחב מעבר לפסיכולוגים | מכפיל את השוק הפוטנציאלי |
| ✅ Multi-tenant על תשתית אחת | חסכוני, פשוט לתחזוקה, סטנדרט בתעשייה |

## 2. הגדרת הבעיה וקהל היעד

### 2.1 הבעיה

בעל מקצוע עצמאי שעובד מול לקוחות חוזרים מבזבז זמן משמעותי על תיאום לוגיסטי. תיאום תור בודד יכול לקחת 4–8 הודעות הלוך ושוב. עבור מטפל עם 25 לקוחות בשבוע, זה עשוי להסתכם בשעות עבודה שאינן מייצרות הכנסה.

בעיות משנה:
- **תורים כפולים** — טעות אנוש ביומן ידני
- **No-shows** — לקוח שוכח, אין תזכורת
- **חוסר גמישות** — ביטול ברגע האחרון משאיר חור בלוח שקשה למלא
- **חוסר מקצועיות** — התכתבות אישית במקום מערכת מסודרת

### 2.2 קהל היעד — פילוח

המערכת מיועדת לבעלי מקצוע עצמאיים שעובדים **פגישות 1-על-1 מתוזמנות**.

#### שכבה א' — Early Adopters (התמקדות ראשונה)

| תחום | מאפיינים | מחיר טיפול ממוצע |
|---|---|---|
| **קאוצ'ינג** (חיים/עסקי/קריירה) | תחום ללא רגולציה, צומח מהר, קהל טכנולוגי | 150–500 ₪ |
| **טיפולי מגע** (עיסוי, שיאצו, רפלקסולוגיה) | הרבה עצמאים, ניהול יומן ידני נפוץ | 200–400 ₪ |
| **אימון אישי / כושר** | קהל צעיר, רגיל לאפליקציות | 150–300 ₪ |

**למה להתחיל כאן:** אין רגולציה על מידע רפואי, פחות רגישות משפטית, קהל פתוח לטכנולוגיה, ומחסום כניסה נמוך.

#### שכבה ב' — הרחבה (חודש 6+)

| תחום | מאפיינים | הערה |
|---|---|---|
| **פסיכולוגים / מטפלים נפשיים** | שוק ענק — כ-16.6 מיליארד ₪/שנה בישראל | דורש זהירות בפרטיות |
| **תזונאים** | פגישות מעקב חוזרות | גבול אפור — לא לאחסן תוכניות תזונה |
| **מורים פרטיים** (מוזיקה, שפות, לימודים) | תדירות גבוהה, לקוחות קבועים | קל |
| **מטפלים אלטרנטיביים** | רייקי, נטורופתיה, דיקור | ללא רגולציה |

### 2.3 פרסונות

#### פרסונה 1: "ליאור" — הקאוצ'ר העצמאי
- בן 38, קאוצ'ר עסקי, 5 שנות ותק
- 20–25 לקוחות פעילים, 4–6 פגישות ביום
- עובד מהקליניקה + זום
- **כאב עיקרי:** מבזבז 45 דקות ביום על תיאומים בווטסאפ
- **מה יגרום לו לשלם:** חיסכון בזמן + מראה מקצועי מול לקוחות
- **מה יגרום לו לנטוש:** אם זה מסובך יותר מיומן גוגל

#### פרסונה 2: "שרה" — המעסה
- בת 45, קליניקה ביתית, 12 שנות ותק
- 30 לקוחות, חלקם קבועים חלקם מזדמנים
- לא טכנולוגית במיוחד
- **כאב עיקרי:** תורים כפולים, ביטולים ברגע האחרון
- **מה יגרום לה לשלם:** תזכורות אוטומטיות שמורידות no-shows
- **מה יגרום לה לנטוש:** ממשק לא ברור, אנגלית

#### פרסונה 3: "דני" — הלקוח
- מגיע דרך קישור שקיבל בווטסאפ
- **לא נרשם, לא מוריד אפליקציה, לא זוכר סיסמה**
- רוצה: לראות זמנים, לבחור, לקבל אישור. 30 שניות.
- **מה יגרום לו לנטוש:** דרישה להירשם, טופס ארוך, ממשק לא מותאם לנייד

> **עקרון מנחה:** חוויית הלקוח (דני) חייבת להיות חסרת חיכוך לחלוטין. הוא לא הלקוח המשלם, אבל אם הוא לא מצליח להזמין — המטפל נוטש את המערכת.

## 3. הגדרת המוצר וגבולות גזרה

### 3.1 מה המערכת עושה (In Scope)

| קטגוריה | יכולת |
|---|---|
| **ניהול זמינות** | פתיחה/סגירה של חלונות טיפול, זמינות חוזרת (recurring), חסימת ימים |
| **דף הזמנה ציבורי** | קישור ייחודי לכל מטפל, ללא צורך בהרשמה של הלקוח |
| **ניהול הזמנות** | צפייה, אישור, ביטול, שינוי מועד |
| **תקשורת** | אישורי הזמנה במייל, תזכורות (מייל/SMS/WhatsApp) |
| **ניהול לקוחות** | רשימת אנשי קשר בסיסית (שם, טלפון, מייל, היסטוריית תורים) |
| **הגדרות אישיות** | משך טיפול, מיקום, מדיניות ביטול, מיתוג בסיסי |
| **מנויים** | הרשמה, שדרוג, ביטול, חיוב חוזר |

### 3.2 מה המערכת **לא** עושה (Out of Scope — החלטה מודעת)

| מה | למה לא |
|---|---|
| ❌ **סיכומי מפגש / תיעוד טיפולי** | חשיפה משפטית למידע רפואי. מוציא את המערכת מגדרי חוק הגנת הפרטיות המחמיר |
| ❌ **סליקה של תשלומי לקוחות** | דורש Stripe Connect, KYC, AML, רישיון נותן שירותי תשלום. מורכבות עצומה |
| ❌ **אבחונים / תוכניות טיפול** | מידע רפואי |
| ❌ **Directory ציבורי של מטפלים** | בעיית "ביצה ותרנגולת", לא רלוונטי ב-MVP |
| ❌ **וידאו / Telehealth מובנה** | Zoom/Meet כבר עושים את זה. אפשר לקשר, לא לבנות |
| ❌ **חשבוניות / הנהלת חשבונות** | תחום נפרד לגמרי, דורש התממשקות לרשות המסים |

> ⚠️ **הערה קריטית:** ההחלטה לא לאחסן מידע רפואי היא **החלטת ארכיטקטורה, לא רק החלטת מוצר**. אין להוסיף שדה "הערות חופשיות" למטפל בלי בחינה משפטית — מטפל ישתמש בו לתיעוד רפואי, וזה יגרור את המערכת לרגולציה שברחנו ממנה.

### 3.3 גבול אפור — שדה "הערות"

מטפלים **ידרשו** שדה הערות. הפתרון המוצע:

```
✅ מותר: שדה "הערה לוגיסטית" מוגבל ל-200 תווים
   דוגמאות: "מגיע עם ילד", "חניה בחצר", "לקוח חדש"

⚠️ חובה: הודעה מפורשת בממשק —
   "שדה זה מיועד להערות לוגיסטיות בלבד.
    אין להזין בו מידע רפואי או אישי רגיש."

📋 תנאי שימוש: האחריות על תוכן השדה היא של המטפל בלבד
```

### 4.3 היגיון התמחור

- **Free** — מנוע רכישה. מספיק שימושי כדי להתאהב, מגביל מספיק כדי לשדרג. הגבול הקריטי: 15 הזמנות/חודש. מטפל פעיל יגיע לזה תוך שבועיים.
- **Basic ($10)** — מתומחר בדיוק כמו Calendly Standard. אין סיבה שמישהו ישלם יותר על אותו דבר.
- **Pro ($25)** — כאן הרווח. SMS ומיתוג הם הפיצ'רים שמצדיקים את הקפיצה.
- **Business ($50)** — למי שיש קליניקה קטנה או מותג מבוסס.

### 4.4 תחזית הכנסות

**הנחות:** התפלגות 40% Free / 35% Basic / 20% Pro / 5% Business

| מספר מטפלים | הכנסה חודשית | הכנסה שנתית (ARR) |
|---|---|---|
| 50 | $550 (~₪2,035) | ~₪24,400 |
| 200 | $2,200 (~₪8,140) | ~₪97,700 |
| 500 | $5,500 (~₪20,350) | ~₪244,000 |
| 1,000 | $11,000 (~₪40,700) | ~₪488,000 |
| 2,500 | $27,500 (~₪101,750) | ~₪1,221,000 |

**נקודת איזון (Break-even):** בהנחת עלויות תפעול של ~$300/חודש בשלב מוקדם — נדרשים כ-**30 מנויים משלמים**.

### 4.5 יחידות כלכליות (Unit Economics)

```
ARPU (הכנסה ממוצעת למשתמש משלם):
  (0.35×10 + 0.20×25 + 0.05×50) / 0.60 = ~$18.75/חודש

LTV (בהנחת churn חודשי של 4%, כלומר חיים ממוצעים של 25 חודשים):
  $18.75 × 25 = ~$469

CAC יעד (כדי לשמור על יחס בריא של 3:1):
  ≤ $156 (~₪577) לרכישת מנוי משלם

Payback period יעד: ≤ 8 חודשים
```

> ⚠️ **אלה מספרים תיאורטיים.** ה-churn האמיתי בכלים לעצמאים נוטה להיות גבוה (5–8% חודשי). יש למדוד מהיום הראשון.

### 5.2 בחירת טכנולוגיות ונימוקים

### 5.3 עקרון Multi-Tenancy

**מודל שנבחר: Shared Database, Shared Schema, Row-Level Isolation**

כל מטפל מקבל `therapist_id` ייחודי. **כל** שאילתה במערכת מסוננת לפי המזהה הזה.

```
Database אחד ← 50 / 500 / 5,000 מטפלים
                  ↓
      כל אחד רואה רק את הנתונים שלו
```

**שכבות ההגנה:**

1. **JWT Token** — מכיל `therapist_id`, נחתם ומאומת
2. **Middleware** — מזריק `therapist_id` לכל בקשה, לא מקבל אותו מהלקוח
3. **Query Layer** — כל שאילתה כוללת `WHERE therapist_id = ?` בכפייה
4. **Row Level Security (RLS)** — הגנה ברמת ה-DB עצמו, גם אם הקוד נכשל

> ⚠️ **כלל ברזל:** ה-`therapist_id` **לעולם** לא מגיע מגוף הבקשה או מפרמטר URL בנתיבים מוגנים. תמיד מה-token בלבד. הפרה של הכלל הזה = דליפת נתונים בין לקוחות.

```typescript
// ❌ אסור — לקוח יכול לזייף
app.get('/api/sessions', (req) => {
  const id = req.query.therapistId;  // מסוכן!
  return db.sessions.findMany({ where: { therapistId: id } });
});

// ✅ נכון — מגיע מה-token בלבד
app.get('/api/sessions', authenticate, (req) => {
  const id = req.auth.therapistId;   // מאומת
  return db.sessions.findMany({ where: { therapistId: id } });
});
```

### 6.3 שיקולי אזורי זמן — קריטי

```
⚠️ כלל ברזל: כל timestamp ב-DB נשמר ב-UTC בלבד (TIMESTAMPTZ).
   ההמרה לאזור זמן מקומי מתבצעת אך ורק בשכבת התצוגה.
```

**למה זה קריטי:** מעברי שעון קיץ/חורף בישראל מתרחשים בתאריכים שונים מאירופה/ארה"ב. מטפל שקבע תור ל-"10:00" ביום שהשעון משתנה, עלול לגלות שהמערכת הזיזה אותו בשעה. שמירה ב-UTC + המרה בתצוגה פותרת את זה.

**מקרה נוסף:** לקוח שנמצא בחו"ל. דף ההזמנה צריך להציג את הזמן **באזור הזמן של המטפל**, עם ציון מפורש: "השעות מוצגות לפי שעון ישראל".

## 9. אפיון API

### 9.1 עקרונות

- REST עם JSON, או tRPC ל-type-safety מלא
- אימות: Bearer JWT מ-Clerk
- Rate limiting על כל נקודת קצה
- כל תגובת שגיאה במבנה אחיד
- Idempotency keys על פעולות כתיבה קריטיות

### 9.2 נקודות קצה — ציבוריות (ללא אימות)

| Method | Endpoint | תיאור |
|---|---|---|
| `GET` | `/api/public/therapists/:slug` | פרטי מטפל לתצוגה (שם, לוגו, מיקום, משך) |
| `GET` | `/api/public/therapists/:slug/availability?from=&to=` | חלונות פנויים בטווח |
| `POST` | `/api/public/sessions/:id/hold` | נעילה זמנית (10 דק') |
| `POST` | `/api/public/bookings` | יצירת הזמנה |
| `GET` | `/api/public/bookings/manage/:token` | פרטי הזמנה לניהול |
| `POST` | `/api/public/bookings/manage/:token/cancel` | ביטול ע"י לקוח |
| `POST` | `/api/public/bookings/manage/:token/reschedule` | שינוי מועד |

**Rate limits ציבוריים:** 30 בקשות/דקה לכתובת IP · 5 הזמנות/שעה לכתובת IP · CAPTCHA אחרי 3 כשלונות.

| מקור | אירועים |
|---|---|
| **Stripe** | `checkout.session.completed`, `customer.subscription.created/updated/deleted`, `invoice.payment_succeeded`, `invoice.payment_failed` |

**דרישות:** אימות חתימה חובה · עיבוד אידמפוטנטי (אותו event פעמיים = תוצאה זהה) · תגובה 200 מהירה, עיבוד ברקע · לוג של כל webhook.

### 9.5 מבנה שגיאות אחיד

```json
{
  "error": {
    "code": "SLOT_ALREADY_BOOKED",
    "message": "המועד שבחרת כבר נתפס. אנא בחר מועד אחר.",

## 10. אבטחה ופרטיות

### 10.1 מדוע ההחלטה על מידע רפואי מפחיתה סיכון

בישראל, מידע על מצב בריאותי (כולל נפשי) מוגדר "מידע רגיש" ומחייב הגנות מוגברות. תיקון 13 לחוק הגנת הפרטיות (2024) החמיר משמעותית את הסנקציות, כולל עיצומים כספיים גבוהים.

**ההחלטה לא לאחסן סיכומי מפגש, אבחונים או מידע רפואי מוציאה את המערכת מהקטגוריה הזו** — היא מחזיקה מידע אישי (שם, טלפון, מייל, זמן פגישה) אך לא מידע רפואי.

⚠️ **אבל:** עצם העובדה שאדם קבע תור אצל פסיכולוג היא **בעצמה** מידע רגיש. לכן:

| דרישה | יישום |
|---|---|
| הצפנה במנוחה | Database encryption at rest (Supabase מספק) |
| הצפנה בתעבורה | TLS 1.3 בלבד, HSTS |
| מינימיזציה | לאסוף רק מה שהכרחי — לא ת.ז., לא כתובת, לא תאריך לידה |
| בידוד | RLS ברמת DB, לא רק ברמת אפליקציה |
| מחיקה | מדיניות שמירה — מחיקת הזמנות ישנות מ-24 חודשים |
| ייצוא | זכות הלקוח לקבל את המידע עליו |

- [ ] CORS מוגדר במפורש (לא `*`)

[2] הכלה        → כיבוי הפיצ'ר הפגוע, לא כל המערכת
[3] הערכה       → מה דלף? כמה משתמשים? מתי התחיל?
[4] תיקון       → פריסת תיקון + אימות
[5] יידוע       → אם דלף מידע אישי:
                   • יידוע המטפלים המושפעים
                   • דיווח לרשות להגנת הפרטיות (יש חובת דיווח!)
[6] תחקיר       → מסמך post-mortem, מה מונע חזרה
```

**הכנה מראש:** כתוב את התוכנית **לפני** האירוע. באמצע משבר אין זמן לחשוב.

### 10.5 מסמכים משפטיים נדרשים

| מסמך | קהל | חובה? |
|---|---|---|
| תנאי שימוש | מטפלים | ✅ |
| מדיניות פרטיות | מטפלים + לקוחות | ✅ |
| הסכם עיבוד מידע (DPA) | מטפלים | ✅ — אתה מעבד מידע בשמם |
| מדיניות עוגיות | כולם | ✅ |
| SLA | מסלול Business | מומלץ |

> 💡 **המלצה:** תקציב של ₪5,000–15,000 לעו"ד המתמחה בהגנת פרטיות ודיני אינטרנט, **לפני** ההשקה. זה זול משמעותית מאשר לתקן אחרי.

## 11. מקרי קצה וטיפול בשגיאות

### 11.1 מקרה קצה #1 — הזמנה כפולה (Race Condition)

**התרחיש:** שני לקוחות לוחצים "אשר" על אותו slot באותה שנייה.

```
❌ ללא הגנה:
   Request A: SELECT status → 'open'
   Request B: SELECT status → 'open'   (עדיין!)
   Request A: UPDATE → 'booked'  ✓
   Request B: UPDATE → 'booked'  ✓     ← שניהם "הצליחו"!
```

**הפתרון — שלוש שכבות:**

```sql
-- שכבה 1: נעילה פסימית ברמת השורה
BEGIN;
  SELECT * FROM sessions
  WHERE id = $1 AND status = 'open'
  FOR UPDATE;                    -- נועל את השורה

  -- אם לא הוחזרה שורה → תפוס, החזר 409

  UPDATE sessions SET status = 'booked' WHERE id = $1;
  INSERT INTO bookings (...) VALUES (...);
COMMIT;

-- שכבה 2: אילוץ ייחודיות ברמת ה-DB
ALTER TABLE bookings ADD CONSTRAINT uq_session UNIQUE (session_id);

-- שכבה 3: מניעת חפיפות זמנים
CREATE EXTENSION btree_gist;
ALTER TABLE sessions ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (
    therapist_id WITH =,
    tstzrange(starts_at, ends_at) WITH &&
  ) WHERE (status IN ('open','held','booked'));
```

**בנוסף — מנגנון Hold:** ברגע שלקוח בוחר שעה ומתחיל למלא טופס, ה-slot עובר ל-`held` עם `hold_expires_at = now() + 10 minutes`. Job רקע משחרר holds שפגו.

### 11.2 מקרה קצה #2 — המטפל מבטל תור מוזמן

```
מטפל לוחץ "בטל" על slot מוזמן
    ↓
דיאלוג אזהרה מפורש:
┌───────────────────────────────────────┐
│ ⚠️ יש הזמנה בזמן זה                  │
│                                       │
│ דנה לוי · 050-1234567                │
│ יום ה', 7.8, 10:00                   │
│                                       │
│ ביטול ישלח הודעה ללקוחה.              │
│                                       │
│ סיבה (אופציונלי, יישלח ללקוחה):      │
│ [_________________________]           │
│                                       │
│ [חזור]        [בטל את התור]          │
└───────────────────────────────────────┘
    ↓
Transaction:
  ├─ booking.status → canceled_by_therapist
  ├─ session.status → canceled
  ├─ ביטול תזכורות ממתינות
  └─ שליחת הודעה מיידית ללקוח (מייל + SMS)
    ↓
ההודעה ללקוח כוללת קישור לקביעה מחדש
```

**מקרה חירום — ביטול יום שלם:** אפשרות "בטל את כל התורים ב-[תאריך]" עם הודעה אחת מרוכזת לכל הלקוחות.

### 11.3 מקרה קצה #3 — שינויים בזמינות מול הזמנות קיימות

| תרחיש | טיפול |
|---|---|
| מטפל משנה משך טיפול מ-50 ל-60 דק' | חל רק על slots **חדשים**. קיימים לא משתנים |
| מטפל מוחק כלל זמינות חוזר | הצעה: "למחוק גם slots עתידיים שנוצרו מהכלל? (X מהם מוזמנים)" |
| מטפל משנה slug | הקישור הישן ממשיך לעבוד 90 יום עם redirect |
| מטפל מוחק חשבון | לקוחות עם תורים עתידיים מקבלים הודעה. דף ההזמנה מציג "המטפל אינו פעיל" |

### 11.4 מקרה קצה #4 — אזורי זמן ושעון קיץ

| תרחיש | טיפול |
|---|---|
| מעבר שעון קיץ/חורף | שמירה ב-UTC פותרת אוטומטית. **חובה בדיקת QA בתאריכי המעבר** |
| לקוח בחו"ל | הצגת השעה באזור המטפל + ציון מפורש: "שעון ישראל (GMT+3)" |
| מטפל נוסע לחו"ל | הגדרות → אזור זמן. אזהרה: "שינוי ישפיע על תצוגת התורים הקיימים" |

### 11.5 מקרה קצה #5 — כשלונות מערכת

| כשל | טיפול |
|---|---|
| שליחת מייל נכשלה | Retry עם exponential backoff (3 ניסיונות). אחרי כשלון סופי — התראה למטפל בדשבורד |
| Webhook מ-Stripe לא הגיע | Job יומי שמסנכרן מול Stripe API. אף פעם לא לסמוך רק על webhooks |
| Database לא זמין | דף שגיאה ידידותי + סטטוס. **לא** להציג stack trace |
| ספק SMS נפל | Fallback למייל + התראה למטפל |

### 11.6 מקרה קצה #6 — התנהגות זדונית

| איום | הגנה |
|---|---|
| Bot ממלא את כל ה-slots | Rate limiting לפי IP + CAPTCHA אחרי 2 הזמנות + אימות מייל |
| Enumeration של slugs | Rate limit על `/book/*`, slugs לא רציפים |
| ניחוש `manage_token` | טוקן אקראי 32 בתים, חד-פעמי, פג תוקף אחרי המפגש |
| Scraping של פרטי לקוחות | ה-API הציבורי **לעולם** לא מחזיר פרטי לקוחות — רק זמינות |
| הזמנות פיקטיביות | מגבלת הזמנות פעילות לכל מייל/טלפון (ברירת מחדל: 3) |

### 12.1 מתי נכנס MCP?

**MCP (Model Context Protocol)** מאפשר למודלי שפה כמו Claude להתחבר למערכות חיצוניות ולבצע בהן פעולות.

**הבחנה חשובה — שני הקשרים נפרדים:**

| הקשר | מתי | סטטוס |
|---|---|---|
| **MCP ככלי פיתוח** — שימוש ב-Claude Code עם MCP servers ל-GitHub/DB בזמן הבנייה | מהיום הראשון | כבר רלוונטי |
| **MCP כפיצ'ר במוצר** — MCP Server שמאפשר למטפל לשאול את Claude "מה הלו״ז שלי השבוע?" | שלב 5, חודש 8+ | לא לפני |

**תנאי סף לפני MCP כפיצ'ר:**

1. ✅ API יציב ומתועד (אי אפשר לעטוף API שמשתנה כל שבוע)
2. ✅ אימות והרשאות מוצקים (MCP חושף פעולות — טעות = דליפה)
3. ✅ מסה קריטית של משתמשים (≥500) שמצדיקה את ההשקעה
4. ✅ ביקוש מוכח — משתמשים ששואלים על זה

**מה זה יאפשר בעתיד:**
```
"Claude, כמה תורים יש לי מחר?"
"Claude, פתח לי חלונות כל יום ג' ב-9 בבוקר לחודש הקרוב"
"Claude, מי ביטל השבוע?"
"Claude, שלח תזכורת לכל התורים של מחר"
```

> 💡 זה יכול להיות **בידול תחרותי אמיתי** — Calendly עדיין לא עשו את זה. אבל זה פיצ'ר של מוצר בוגר, לא של MVP. לבנות אותו מוקדם מדי זה לבזבז 3 שבועות על משהו ש-2% מהמשתמשים ישתמשו בו.
