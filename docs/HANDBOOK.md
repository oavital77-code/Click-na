# Cleana+ — מדריך הפעלה, בנייה ותחזוקה

המסמך הזה הוא הדבר היחיד שצריך לקרוא כדי להריץ את המערכת, להבין למה היא
בנויה כך, ולתקן אותה כשמשהו נשבר. האפיון המוצרי המקורי נמצא ב-
[`product-spec.md`](product-spec.md); כאן מתועדת המערכת **כפי שהיא בנויה
בפועל**.

המוצר האחות, Cleana (SaaS לקליניקות), חי בריפו נפרד — `oavital77-code/cleanasaas`.
שני המוצרים נפגשים בדיוק בנקודה אחת, דשבורד הבעלים, שמתועדת בפרק 11.

---

## 1. מה זה

מערכת לניהול תורים למטפלים ובעלי מקצוע **עצמאיים** — מטפל אחד, הלקוחות
שלו, היומן שלו. לא מערכת לקליניקה עם כמה מטפלים; זה בדיוק מה ש-Cleana
SaaS עושה.

מה שמטפל מקבל:

- **דף הזמנה ציבורי** בכתובת `/book/<slug>` — הלקוח בוחר מועד מתוך הזמינות
  האמיתית ומזמין בעצמו, בלי חשבון ובלי התכתבות.
- **ניהול זמינות** בכללים חוזרים ("ראשון 09:00–13:00, פגישה 50 דקות"),
  שמהם נגזרים מועדים פנויים בפועל.
- **דשבורד** להזמנות, לקוחות, הודעות והגדרות.
- **מיילים אוטומטיים**: אישור הזמנה עם קובץ יומן, התראה למטפל, תזכורת לפני
  הפגישה, והודעות ביטול.
- **קישור ניהול** לכל הזמנה — הלקוח מבטל או מזיז מועד בעצמו, בלי חשבון.

השפה: עברית ואנגלית, RTL מלא. אזור זמן ברירת מחדל `Asia/Jerusalem`.

## 2. ארכיטקטורה במבט אחד

```
                        ┌──────────────────────────┐
   לקוח (ללא חשבון) ──▶ │  /book/<slug>            │
                        │  /api/public/*           │
                        └────────────┬─────────────┘
                                     │
   מטפל (Clerk) ──────▶ ┌────────────▼─────────────┐      ┌──────────┐
                        │  Next.js 16 (App Router) │─────▶│ Postgres │
   Vercel Cron ────────▶ │  על Vercel               │      │ + Prisma │
                        └────────────┬─────────────┘      └──────────┘
                                     │
                        ┌────────────┴───────────────┐
                        ▼             ▼              ▼
                     Clerk         Resend         PayPlus
                    (זהות)        (מיילים)       (תשלומים)
```

| רכיב | בחירה | למה |
| --- | --- | --- |
| Framework | Next.js 16, App Router | Server Components — שאילתת DB רצה בשרת בלי שכבת API באמצע |
| שפה | TypeScript, `strict` | |
| DB | PostgreSQL | מניעת חפיפת תורים נאכפת ב-DB עצמו, לא בקוד |
| ORM | Prisma 7 + `@prisma/adapter-pg` | |
| זהות | Clerk | מטפלים בלבד. ללקוחות אין חשבון בכוונה |
| מייל | Resend | |
| תשלומים | PayPlus (טוקן) | ר' פרק 8 |
| אירוח | Vercel + Vercel Cron | |
| בדיקות | Vitest | 378 בדיקות, כולל אינטגרציה מול Postgres אמיתי |

**עקרון־על:** כל שורה שייכת למטפל אחד (`therapist_id`), וה-`therapist_id`
**תמיד** נגזר בשרת מזהות ה-Clerk — לעולם לא מתקבל כפרמטר מהלקוח. זה החוק
שמונע ממטפל אחד לראות הזמנות של אחר, והוא נאכף ב-`src/lib/auth.ts`.

## 3. הרצה מקומית

**דרישות:** Node 22+, PostgreSQL 14+ מקומי.

```bash
git clone https://github.com/oavital77-code/Click-na.git
cd Click-na

npm install                    # מריץ prisma generate אוטומטית (postinstall)

cp .env.example .env           # ואז למלא — ר' פרק 4
createdb cleana_dev            # או כל שם, בהתאמה ל-DATABASE_URL

npm run db:migrate             # מחיל את כל המיגרציות
npm run dev                    # http://localhost:3000
```

**המינימום שבאמת צריך כדי להריץ:** `DATABASE_URL` ומפתחות Clerk. בלי
Clerk האפליקציה לא עולה בכלל. אין חשבון Clerk? `npx clerk@latest init
--keyless` מייצר מפתחות פיתוח זמניים.

כל השאר אופציונלי ונכשל בחן: בלי `RESEND_API_KEY` המייל לא נשלח אבל
ההזמנה עוברת (נרשמת `Notification` בסטטוס `failed`); בלי מפתחות PayPlus
כפתור התשלום לא מוצג וההתנסות ממשיכה כרגיל.

פקודות:

| פקודה | מה עושה |

| `npm run dev` | שרת פיתוח |
| `npm run build` | בניית פרודקשן |

## 4. משתני סביבה

הרשימה המלאה עם הסברים נמצאת ב-[`.env.example`](../.env.example). התקציר:

### חובה

| משתנה | מה זה |
| --- | --- |
| `DATABASE_URL` | חיבור Postgres. **בפרודקשן: ה-pooler** (פורט 6543, `pgbouncer=true`) |
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` · `CLERK_SECRET_KEY` | זהות. בלעדיהם האפליקציה לא עולה |
| `NEXT_PUBLIC_APP_URL` | מקור הפריסה. **קריטי בפרודקשן** — כל קישור במייל נבנה ממנו |
| `CRON_SECRET` | מאמת את Vercel Cron. בלעדיו ה-route מחזיר 503 בפרודקשן |

### פרודקשן

| משתנה | מה זה |
| --- | --- |
| `DIRECT_URL` | חיבור לא-pooled (5432) למיגרציות בלבד — pgbouncer לא מריץ DDL |
| `CLERK_WEBHOOK_SIGNING_SECRET` | ל-`/api/webhooks/clerk` (`user.created`, `user.deleted`) |
| `RESEND_API_KEY` · `EMAIL_FROM` | `EMAIL_FROM` חייב להיות דומיין מאומת **בחשבון הזה** |
| `INTEGRATION_ENCRYPTION_KEY` | 32 בייטים base64. מצפין אישורי צד־שלישי של מטפלים |
| `PAYPLUS_API_KEY` · `PAYPLUS_SECRET_KEY` · `PAYPLUS_PAYMENT_PAGE_UID` | שלושתם או שהתשלום לא מוצע |
| `PLAN_PRICE_ILS` | מחיר חודשי בש"ח כולל מע"מ. ברירת מחדל בקוד: 79 |
| `OWNER_STATS_SECRET` | סוד משותף לדשבורד הבעלים — ר' פרק 11 |

### אופציונלי

`PAYPLUS_TERMINAL_UID`, `PAYPLUS_CASHIER_UID` (נלכדים אוטומטית מה-callback
הראשון; אלה דורסים), `PAYPLUS_BASE_URL` (סנדבוקס), `OWNER_NOTIFICATION_EMAIL`
(התראה על הרשמה חדשה).

> **`INTEGRATION_ENCRYPTION_KEY` — שינוי הערך הופך כל אישור שמור לבלתי
> קריא**, וכל מטפל צריך להזין מחדש. לא לסובב אותו בלי תוכנית.

## 5. מודל הנתונים

הסכמה המלאה: [`prisma/schema.prisma`](../prisma/schema.prisma).

```
Therapist ─┬─ TherapistSettings   (1:1)  מדיניות: התראה מוקדמת, חוצץ, טווח
           ├─ Subscription        (1:1)  מצב החיוב — פרק 8
           ├─ AvailabilityRule    (1:N)  "ראשון 09:00–13:00, 50 דקות"
           ├─ Session             (1:N)  מועד קונקרטי: open / held / booked / blocked
           │    └─ Booking        (1:1)  ההזמנה שתפסה את המועד
           ├─ Client              (1:N)
           ├─ Integration         (1:N)  אישורי צד־שלישי, מוצפנים
           ├─ Payment             (1:N)  תשלומי PayPlus
           ├─ Notification        (1:N)  כל מייל: מתוזמן / נשלח / נכשל
           ├─ SlugRedirect        (1:N)  קישור ישן ממשיך לעבוד אחרי שינוי slug
           └─ AuditLog            (1:N)
```

שלוש החלטות ששווה להכיר:

**`Session` נפרד מ-`Booking`.** המועד קיים לפני שמישהו הזמין אותו, ושורד
ביטול. זה מה שמאפשר "החזק 10 דקות בזמן מילוי הטופס" בלי ליצור הזמנה
מדומה, וזה מה שמאפשר לבטל בלי לאבד את המשבצת.

**מניעת חפיפה נאכפת ב-DB.** GiST exclusion constraint על טווח הזמן של
`Session` — שני לקוחות שלוחצים "אשר" באותה שנייה על אותו מועד, אחד מקבל
שגיאת DB. תנאי מרוץ שנפתר בקוד בלבד תמיד יפספס מקרה קצה.

**צילום פרטי הלקוח על ההזמנה** (`client_name_snapshot` ואחיו). לקוח
שמעדכן טלפון לא משנה רטרואקטיבית מה היה כתוב בהזמנה מלפני חצי שנה.

## 6. הזרימות המרכזיות

### הזמנה ציבורית

```
לקוח פותח /book/<slug>
  └─▶ GET /api/public/therapists/<slug>/availability   ← מוגבל 120/דקה לכתובת IP
        מחשב מועדים פנויים מהכללים + ההזמנות הקיימות + מדיניות ההתראה המוקדמת
  └─▶ POST /api/public/sessions/<id>/hold
        תופס את המועד ל-10 דקות (hold_expires_at) — לא הזמנה, רק שריון
  └─▶ POST /api/public/bookings
        טרנזקציה אחת: אימות ההחזקה → יצירת/איתור לקוח → Booking → manage_token
  └─▶ מייל אישור ללקוח (עם ICS) + התראה למטפל
```

ההחזקה היא שמונעת את התסכול הקלאסי: הלקוח ממלא טופס דקה שלמה, ומגלה
בסוף שהמועד נתפס. החזקה שפגה משוחררת בקריאה הבאה לזמינות — אין צורך
בעבודה מתוזמנת.

### קישור ניהול

לכל הזמנה יש `manage_token` — מחרוזת אקראית של 64 תווים, ייחודית, שנשלחת
במייל האישור. `/book/<slug>/manage/<token>` מאפשר ללקוח לבטל או להזיז
מועד. **הטוקן הוא ההרשאה**, ולכן: הוא נבדק בזמן קבוע, הוא לא מופיע
בלוגים, והוא נותן גישה להזמנה אחת בלבד.

### תזכורות

`/api/cron/send-reminders` רץ כל יום ב-06:00 UTC ועושה שלושה דברים:

1. **תזכורות שהגיע זמנן** — `sendDueReminders()`. עובד במנות של 150 עם
   מקביליות 3 (`REMINDER_BATCH`, `REMINDER_CONCURRENCY` ב-`notifications.ts`).
   לולאה סדרתית ללא תקרה הייתה חורגת מזמן הריצה ברגע שיש מספיק מטפלים.
2. **מחזור החיים של החיוב** — פרק 8.
3. **ניקוי חלונות הגבלת הקצב** שכבר נסגרו.

## 7. אבטחה

מה שמגן על המערכת, לפי שכבות:

**זהות והפרדה.** כל נתיב מאומת שואב `therapist_id` מ-Clerk בשרת
(`src/lib/auth.ts`). לקוח לא יכול לבקש נתונים של מטפל אחר, כי ה-id שלו לא
עובר בבקשה כלל.

**RLS מופעל על כל הטבלאות — בלי מדיניות.** זה נשמע כמו טעות, והוא לא.
המערכת לא ניגשת ל-DB דרך הלקוח של Supabase אלא ישירות דרך Prisma, כבעלת
הטבלאות, וההרשאות נאכפות בקוד לפי ה-`therapistId` שנגזר מהסשן. אבל אם
ה-DB מתארח ב-Supabase, PostgREST חושפת כל טבלה לתפקידי `anon` ו-
`authenticated` — ומי שמחזיק במפתח הפומבי היה קורא וכותב כל שורה. RLS
פעיל בלי מדיניות פירושו **דחייה מוחלטת** לתפקידים האלה, ושקיפות מלאה
לבעלת הטבלאות. אומת בפועל: תפקיד עם הרשאות `SELECT/INSERT/UPDATE/DELETE`
מלאות רואה אפס שורות ולא מצליח לכתוב.
(`20260905120000_enable_row_level_security`)

**הנתיבים הציבוריים** (`/api/public/*`) הם המשטח הפתוח היחיד. הגבלת הקצב
נשמרת בטבלת `rate_limits` ב-Postgres ולא בזיכרון — אחרת כל מופע serverless
היה סופר לעצמו, וההגבלה הייתה מוכפלת במספר המופעים:

| נתיב | תקרה |
| --- | --- |
| `GET /api/public/therapists/[slug]/availability` | 120 לדקה לכתובת IP |
| `POST /api/public/sessions/[id]/hold` | 30 לעשר דקות לכתובת IP |
| `POST /api/public/bookings` | 10 לשעה לכתובת IP |

קישורי הניהול מוגנים בטוקן אקראי בן 64 תווים, לא במזהה שאפשר לנחש.

**סודות של מטפלים.** אישורים שמטפל מזין בלשונית התוספות (מפתח Stripe שלו,
טוקן Twilio, סוד Zoom) מוצפנים ב-`INTEGRATION_ENCRYPTION_KEY` לפני הכתיבה
ל-DB — `src/lib/secret-box.ts`.

**ה-cron.** `Authorization: Bearer <CRON_SECRET>` בהשוואה בזמן קבוע
(SHA-256 ואז `timingSafeEqual`). השוואת מחרוזות רגילה מדליפה את הסוד בית
אחרי בית דרך זמן התגובה. בלי סוד מוגדר, הנתיב מחזיר 503 בפרודקשן — נכשל
סגור, במכוון.

**callback של PayPlus.** נבדקת חתימת HMAC-SHA256 על גוף הבקשה הגולמי,
והעסקה מאומתת מול PayPlus בקריאה נפרדת לפני שנוגעים ב-DB. ההסבר המלא
בפרק 8.

**כותרות אבטחה ו-CSP.** HSTS, `X-Frame-Options`, `X-Content-Type-Options`,
`Referrer-Policy` ו-`Permissions-Policy` מוגדרות ב-`next.config.ts`. ה-CSP
נבנה בנפרד ב-`src/proxy.ts` דרך `clerkMiddleware`, כי הוא נושא nonce שנוצר
מחדש בכל בקשה ורשימת המקורות ש-Clerk צריך היא של Clerk לתחזק (למשל מסגרת
ה-Turnstile של הגנת הבוטים — מדיניות שנכתבת ביד הייתה שוכחת אותה ושוברת
את ההרשמה בשקט).

**המשמעות המעשית:** עמוד שנבנה מראש לא יכול לשאת nonce לכל בקשה,
והסקריפטים שלו היו נחסמים — בפרודקשן בלבד. לכן `/`, `/terms`, `/privacy`
ו-`/cookies` מסומנים `force-dynamic`. זו הסיבה, אם תהיתם.

**מה שסורק אוטומטית:** ר' [`SECURITY.md`](../SECURITY.md).

## 8. חיוב

### התוכנית

תוכנית אחת. `PLAN_PRICE_ILS` ש"ח לחודש כולל מע"מ (ברירת מחדל 79),
**30 יום התנסות**, ואז **7 ימי חסד** לפני נעילה. כל הקבועים במקום אחד:
[`src/lib/plan.ts`](../src/lib/plan.ts).

### מכונת המצבים

`accessState()` ב-[`src/lib/access.ts`](../src/lib/access.ts) היא הפונקציה
**היחידה** שמכריעה מה מותר למטפל עכשיו. הבאנר בדשבורד, הנעילה, ה-402
ב-API וה-cron — כולם שואלים אותה, ולכן הם לא יכולים לסתור זה את זה.

```
trialing ──(30 יום)──▶ grace ──(7 ימים)──▶ locked
    │                    │
    └──── שולם ──────────┴──▶ active ──(תקופה נגמרה, חיוב נכשל)──▶ grace
                                 │
                                 └── ביטול ──▶ canceling ──▶ locked
```

שתי החלטות מכוונות:

- **מצב חסד ננעל לכתיבה, לא לקריאה.** מטפל שלא שילם עדיין רואה את היומן
  שלו. הוא לא נעול מחוץ לנתונים של עצמו.
- **הלקוחות אף פעם לא נענשים.** `acceptsNewBookings()` ממשיך לקבל הזמנות
  גם בנעילה, חוץ ממטפל שביטל את המנוי במפורש — כלומר הודיע שהוא סוגר.
  תזכורות וקישורי ניהול ממשיכים לעבוד תמיד.

### למה טוקן ולא הוראת קבע

מודול החיובים החוזרים של PayPlus לא מופעל בחשבון. במקום זאת אנחנו שומרים
**טוקן תשלום** בחיוב הראשון ומחייבים אותו בעצמנו מה-cron. זה נותן שליטה
מלאה על מועד החיוב ועל מדיניות הניסיון החוזר, במחיר של אחריות: אם ה-cron
לא רץ, אף אחד לא מחויב.

**הזרימה:**

1. `POST /api/billing/checkout` → `PaymentPages/generateLink` עם
   `charge_method: 1` ו-`create_token: true`. המטפל מועבר לדף התשלום.
2. PayPlus קורא ל-`/api/billing/payplus/callback`. שם, לפי הסדר: הגבלת
   קצב → אימות חתימת HMAC → **אימות העסקה מול PayPlus** (`PaymentPages/ipn`)
   → החלה על ה-DB.
3. נשמרים הטוקן, `customer_uid`, `terminal_uid` ו-`cashier_uid`. השניים
   האחרונים הם קבועי חשבון שאף נקודת קצה לא מחזירה — הם מגיעים רק
   ב-callback, ובלעדיהם אי אפשר לחייב טוקן.
4. חידוש: `chargeDueRenewals()` ב-[`src/lib/billing.ts`](../src/lib/billing.ts)
   מחייבת כל טוקן שתקופתו נגמרה, דרך `Transactions/Charge` עם `use_token`.

**מלכודות PayPlus שכבר עלו בדם:**

- `credit_terms: 1` **חובה** ב-`Transactions/Charge`. בלעדיו חוזר
  `credit-terms-incorrect`.
- `more_info` מוגבל ל-**19 תווים**. הוא נושא תווית, לא מזהה חשבון.
- אם ה-callback לא החזיר טוקן, `Token/List` עם `terminal_uid` +
  `customer_uid` הוא הדרך היחידה לשחזר אותו.
- קוד הצלחה הוא המחרוזת `"000"`, לא מספר.
- PayPlus מקננת מזהים בעומקים משתנים, ולכן `parseTransaction` מחפשת
  בסריקה לרוחב חסומה במקום בנתיב קבוע.

**מה מגן על הכסף:**

| סיכון | ההגנה |
| --- | --- |
| callback מזויף | חתימת HMAC **ובנוסף** אימות מול PayPlus |
| callback כפול | ייחודיות על `transaction_uid` — החלה שנייה לא עושה כלום |
| סכום שגוי | הסכום נבדק מול המחיר המוגדר לפני הזיכוי |
| שני cron מחייבים יחד | שורה נתפסת ב-`updateMany` מותנה על `lastChargeAttemptAt` לפני הקריאה ל-PayPlus |
| callback שאבד | תקופה ששולמה ונגמרה בלי חידוש מאושר עוברת לחסד אחרי יומיים — לעולם לא שירות חינם לנצח |

## 10. פריסה

מתארחת ב-Vercel, פרויקט `click-na`, דומיין `cleanaplus.cleanagroup.app`.
דחיפה ל-`main` פורסת לפרודקשן.

**רשימת בדיקה לפני פריסה ראשונה:**

1. כל משתני הסביבה של פרק 4 מוגדרים ב-Vercel, scope **Production**.
2. `DATABASE_URL` מצביע ל-**pooler** (6543, `pgbouncer=true`), ו-`DIRECT_URL`
   לחיבור הישיר (5432). Serverless פותח חיבור לכל מופע; בלי pooler
   Postgres נגמר לו מקום בחיבורים הרבה לפני שנגמרים המשתמשים.
3. המיגרציות הוחלו על ה-DB של פרודקשן.
4. `NEXT_PUBLIC_APP_URL` הוא המקור האמיתי. אם לא — כל קישור במייל מצביע
   ל-localhost.
5. `EMAIL_FROM` על דומיין מאומת ב-Resend.
6. Webhook של Clerk מצביע ל-`/api/webhooks/clerk`.
7. ה-cron מופיע ב-Vercel → Settings → Cron Jobs.

**האזור.** ה-DB בפרנקפורט. הפריסה צריכה להיות באותו אזור — כל hop מיותר
בין הפונקציה ל-DB מוכפל במספר השאילתות בכל בקשה.

## 11. דשבורד הבעלים

מסך אחד שמראה מי קנה את **שני** המוצרים, מתי, ובאיזה סטטוס. הוא חי בצד

```
cleanas.cleanagroup.app/superadmin/owner
        │
        ├─ CleanaS: קריאה ישירה ל-Supabase (service role)
        │
        └─ Cleana+: GET https://cleanaplus.cleanagroup.app/api/owner/stats
                    Authorization: Bearer <OWNER_STATS_SECRET>
```

הצד שבריפו הזה הוא [`src/app/api/owner/stats/route.ts`](../src/app/api/owner/stats/route.ts):
מאומת בטוקן נושא, בהשוואת SHA-256 בזמן קבוע, ומחזיר סכומים ושורה לכל חשבון.

**`OWNER_STATS_SECRET` חייב להיות אותו ערך בדיוק בשני פרויקטי Vercel.**
זה מקור התקלה הנפוץ היחיד כאן:

| מה רואים | מה קרה |
| --- | --- |
| "OWNER_STATS_SECRET לא מוגדר" | חסר בצד CleanaS, או שלא נעשה Redeploy שם |
| Cleana+ החזיר 503 | חסר בצד הזה, או שלא נעשה Redeploy כאן |
| Cleana+ החזיר 401 | מוגדר בשניהם אבל הערכים שונים (בדרך כלל רווח נגרר) |

## 12. Runbook

**מיילים לא נשלחים.** בדקו `RESEND_API_KEY` ו-`EMAIL_FROM`. הסיבה הנפוצה:
`EMAIL_FROM` על דומיין שלא אומת בחשבון Resend **הזה**. כל ניסיון נרשם
בטבלת `Notification` עם `errorMessage` — שם התשובה האמיתית של Resend.

**קישורים במייל מצביעים ל-localhost.** `NEXT_PUBLIC_APP_URL` לא הוגדר
בפרודקשן. זה משתנה זמן־בנייה: אחרי תיקון צריך **Redeploy**, לא רק שמירה.

**ה-cron לא רץ.** 401 = `CRON_SECRET` שונה בין Vercel לפרויקט. 503 =
לא מוגדר כלל. הריצו ידנית מול staging עם אותו header כדי לוודא.

**מטפל ננעל בטעות.** הריצו את `accessState()` על השורה שלו לפני שנוגעים
ב-DB — היא מסבירה בדיוק למה. בדרך כלל `graceEndsAt` שעבר, או תקופה
ששולמה ושהחידוש שלה לא אושר תוך יומיים (ר' פרק 8).

**תשלום נכשל עם `provider_error`.** ההודעה על המסך היא ההודעה של PayPlus
עצמה, במכוון — `providerDetail()` מעביר אותה כלשונה במקום להחליף ב"נסה
שוב" גנרי. `THIS COMPANY DONT HAVE THE PERMISSION TO USE THE API` היא
הרשאת חשבון אצל PayPlus, לא באג אצלנו.

**חיובים כפולים.** לא אמור לקרות — `transaction_uid` ייחודי, ושורה
נתפסת לפני הקריאה ל-PayPlus. אם בכל זאת: בדקו את טבלת `Payment` לפי
`transaction_uid` לפני שמזכים ידנית.

**חריגה מזמן ריצה ב-cron.** `maxDuration = 60` היא התקרה של תוכנית Hobby.
בתוכנית Pro אפשר להעלות. אם התזכורות לא מספיקות להישלח — הגדילו את
`REMINDER_CONCURRENCY` לפני שמגדילים את החלון.
